# Руководство: что сделано, зачем и как это рассказать

Этот файл — ваша шпаргалка. Для каждого этапа есть: **что делаем**, **зачем**, **где в коде**, **что показать в видео**.
Этапы идут в том порядке, в котором проект строился, так что рассказывать можно так же.

---

## 0. Как читать проект

```
db/init.sql            ← база данных
backend/src/*          ← сервер (REST, JWT, WebSocket)
frontend/src/*         ← интерфейс
frontend/tests/*       ← unit-тесты фронтенда
frontend/mock/*        ← тестовый API для запуска одного фронтенда (этап 1)
Dockerfile, compose    ← упаковка
```

Данные ходят так:

```
Браузер ──(React, Redux)──► Next.js ──(REST /api)──► Express ──(SQL)──► MySQL
   ▲                          │ SSR: первый HTML уже с данными
   └────────── WebSocket (Socket.io): счётчик вкладок ────────────────┘
```

Работа шла в два этапа:
1. **Фронтенд отдельно** (`npm run dev:mock`): интерфейс с тестовым API в памяти, без Docker и базы. См. `STAGE1.md`.
2. **Весь стек в Docker** (`docker compose up --build`): MySQL + настоящий бэкенд + фронтенд. Фронтенд при этом не меняется, потому что тестовый API отдаёт те же URL и тот же JSON.

**Нюансы ТЗ, которые мы решили сознательно:**
- В `app.js` из ТЗ нет запятой после `specification: 'Specification 1'` (файл не парсится) и у всех продуктов одинаковое название. Тестовые данные в `init.sql` исправлены и разнообразны (разные типы), иначе фильтр по типу невозможно проверить.
- Продукт ссылается на приход через `order`, а в `app.js` геттер `products` отдавал *все* продукты. Мы строим связь по `order_id`.
- Фильтр в тексте ТЗ — «1 селект», а на макете их два (Тип и Спецификация). Реализованы оба: это включает требование из текста.
- Мелкий формат даты на макете: «04 / 12» над «06 / Апр / 2017», где 04 — номер месяца. Сделано так же.
- Типы продуктов (Monitors, Keyboards, Mice) приходят из данных и не переводятся: переведён интерфейс, а не содержимое.

**В видео:** покажите PDF и таблицу выше: «вот требования, вот где они закрыты».

## 2. База данных (`db/init.sql`)

**Что делаем.** Четыре таблицы:
- `orders` — приходы (название, описание, координаты для карты);
- `products` — продукты, `order_id` → `orders.id`;
- `prices` — цены продукта: отдельная строка на каждую валюту;
- `users` — пользователи для JWT (пароль хранится как bcrypt-хеш).

**Зачем так.**
- Цены в отдельной таблице, а не в колонках `price_usd`, `price_uah`: в `app.js` они массив (`price: [{value, symbol, isDefault}]`); новая валюта — это новая строка, а не новая колонка.
- `ON DELETE CASCADE`: удалили приход — продукты и их цены исчезают сами, база не остаётся в «битом» состоянии.
- Индекс на `products.type` — фильтр по типу работает быстро.
- В начале файла `SET NAMES utf8mb4`: без этого кириллица могла сохраниться «кракозябрами» (мы это реально поймали при проверке).
- Выбрана MySQL, потому что в ТЗ требуется схема, открывающаяся в MySQL Workbench, и данные реляционные (приход → продукты → цены).

**Где:** `db/init.sql`. **В видео:** откройте в MySQL Workbench (инструкция в README), покажите диаграмму связей.

## 3. Бэкенд (`backend/src`)

**Что делаем.** Сервер на Express + TypeScript, разбитый на слои, где каждый файл делает одно дело:

| Файл | Ответственность |
|---|---|
| `db.ts` | пул подключений к MySQL; `waitForDb` ждёт, пока база стартует в Docker |
| `repo.ts` | все SQL-запросы; превращает строки БД (`serial_number`) в формат ТЗ (`serialNumber`, `price: [...]`) |
| `validate.ts` | проверка тела запросов (чистая функция — легко тестируется) |
| `auth.ts` | вход (bcrypt + JWT) и middleware `requireAuth` |
| `index.ts` | маршруты REST + Socket.io + запуск |

**Важные решения.**
- SQL только с параметрами (`?`) — защита от SQL-инъекций. Фильтры по типу и спецификации собираются в `WHERE` только из реально заданных значений.
- Создание продукта — **транзакция**: продукт и две цены добавляются вместе или не добавляются вовсе.
- Чтение открыто (нужно для SSR), изменения — только с JWT. Список пользователей тоже только с JWT, и хеши паролей наружу не отдаются.
- Счётчик вкладок: на каждое подключение/отключение сервер рассылает всем `sessions` = количество сокетов.

**Как работает JWT:** `POST /api/auth/login` → проверяем пароль через bcrypt → подписываем токен (`HS256`, живёт 8 часов) → клиент кладёт его в заголовок `Authorization: Bearer …` → `requireAuth` проверяет подпись. Токен **не шифруется**, а подписывается: данные внутри читаются, но подделать их нельзя.

**В видео:** покажите несколько `curl`-запросов (есть примеры в разделе 17): без токена → 401, с токеном → 201.

## 4. Каркас фронтенда (Next.js App Router)

**Что делаем.**
- `app/layout.tsx` — общая оболочка: `TopMenu` сверху, `NavMenu` слева, страница в `<main>`.
- `app/template.tsx` — в отличие от layout **перемонтируется при каждом переходе**, поэтому CSS-анимация `page-in` играет на каждую навигацию. Это и есть «анимация при переходе между роутами».

**Зачем Next.js.** Требование Junior+ про SSR: первый HTML приходит от сервера уже с данными (быстрый первый показ, SEO).

**В видео:** кликните между «Приход» и «Продукты» — видна плавная анимация. В DevTools → Network → Doc покажите, что ответ сервера уже содержит данные.

## 5. Redux (`store/`)

**Что делаем.** Redux Toolkit, четыре среза:
- `authSlice` — токен и имя пользователя; thunk-и `login` и `logout`;
- `ordersSlice` — список приходов; thunk-и `createOrder`, `deleteOrder`, `createProduct`, `deleteProduct`;
- `productsSlice` — продукты, типы, спецификации и выбранные фильтры; thunk `loadProducts({type, specification})`;
- `searchSlice` — текст из строки поиска в шапке.

**Ключевые идеи.**
- `makeStore()` — фабрика, а не готовый объект: на сервере у каждого запроса свой стор, иначе данные разных пользователей смешались бы.
- Все изменения (создать/удалить) идут по общему шаблону `mutation(...)`: запрос к API с токеном → если успешно, перезагрузить список. Ошибка возвращается через `rejectWithValue`.
- Фильтры продуктов запоминаются сразу при выборе, а запоздавший ответ на старый запрос игнорируется (защита от гонки: иначе при быстром переключении двух фильтров второй брал бы старое значение первого).
- Типизированные хуки: `useAppDispatch`, `useAppSelector` (`store/hooks.ts`).

## 6. SSR и гидратация

**Проблема.** Страница `/orders` рендерится на сервере, а Redux-стор живёт в браузере. Нужно, чтобы сервер и браузер нарисовали **одинаковую** разметку, иначе React выдаст ошибку гидратации.

**Решение.**
1. `app/orders/page.tsx` — серверный компонент: `await api.orders()` (прямой запрос к бэкенду).
2. Передаёт данные клиентскому `OrdersView` как `initial`.
3. `useHydrate(() => setOrders(initial))` (`hooks/useHydrate.ts`) кладёт их в Redux **до первого рендера**.

**Мелкие, но важные детали:**
- Часы в `TopMenu` рендерятся только после монтирования (`now === null` на сервере): время сервера и браузера разное.
- Даты разбираются вручную (`utils/format.ts → parseDate`), а не `new Date(string)`: иначе часовые пояса дали бы разный результат на сервере и в браузере.
- `export const dynamic = 'force-dynamic'` — данные всегда свежие.

**В видео:** `View Page Source` → видны названия приходов прямо в HTML.

## 7. Страницы «Приход» и «Продукты», поиск

**Приход (`OrdersView.tsx`).**
- Клик по строке → `openId` в состоянии → рядом появляется `order-details`; список сжимается («compact»), как на макете. Крестик закрывает панель.
- Две даты: `formatMonthOfYear` («04 / 12») и `formatLong` («06 / Апр / 2017») — названия месяцев зависят от языка.
- Сумма: `orderTotals()` (`utils/totals.ts`) складывает цены всех продуктов **отдельно по каждой валюте**; округление до копеек защищает от `0.1 + 0.2`. Выводит `Money.tsx`: дополнительная валюта мелко сверху, основная — крупно.
- Кнопка удаления → `ConfirmModal` со списком продуктов → подтверждение → thunk `deleteOrder`.
- Слово «Продукта» меняется по правилам языка (`pluralKey` → 1 продукт, 2 продукта, 5 продуктов).

**Продукты (`ProductsView.tsx`).**
- Два select: тип и спецификация. Изменение → `loadProducts({type, specification})` → `GET /api/products?type=…&specification=…` (REST-запрос); пока грузится, список полупрозрачный.
- Гарантия показана в двух форматах: «06 / 04 / 2017» и «06 / Апр / 2017».

**Поиск (поле в шапке, `TopMenu.tsx`).**
1. `onChange` кладёт текст в Redux (`searchSlice`).
2. `OrdersView` и `ProductsView` сами читают `query` и фильтруют уже загруженные данные: `matchesOrder` и `matchesProduct` из `utils/search.ts`.
3. Запроса к серверу нет, поэтому поиск мгновенный. Поиск без учёта регистра, по части слова; для продуктов — по названию, серийному номеру, типу, спецификации и названию прихода; для приходов — по названию, описанию и продуктам внутри.
4. На страницах «Статистика», «Карта», «Пользователи» и «Настройки» поиск ничего не фильтрует.

**В видео:** открыть/закрыть панель, удалить через попап (отменить и подтвердить), поменять фильтры, ввести текст в поиск.

## 8. Формы и валидация

**Что делаем.** Три формы: вход, новый приход, новый продукт. Поля — компонент `TextField` на классах Bootstrap (`is-invalid`, `invalid-feedback`).

**Две линии защиты:**
1. **Клиент** (`validation/`) — мгновенная обратная связь, ошибки локализованы. Возвращает ключи словаря (`errTitle`), а не готовые тексты. Файлы: `rules.ts` (мелкие правила), `order.ts`, `product.ts`, `login.ts`, `errors.ts`.
2. **Сервер** (`backend/src/validate.ts`) — клиенту доверять нельзя: запрос можно отправить и без интерфейса.

**UX-деталь:** ошибка пропадает, как только поле исправлено (`keepUnfixed`), но новые ошибки в ещё не тронутых полях не появляются до нажатия «Сохранить».

Правила: название ≥ 3 символа; координаты — обе или ни одной (широта −90…90, долгота −180…180); серийный номер — положительное целое; цены ≥ 0 (запятая как десятичный разделитель тоже работает); дата окончания гарантии не раньше начала; логин ≥ 3, пароль ≥ 6.

## 9. JWT и Web Storage

**Поток входа:**
1. `LoginForm` → thunk `login` → `POST /api/auth/login`.
2. Ответ `{token, login}` сохраняется **в Redux и в `localStorage`** (`utils/storage.ts`).
3. При открытии страницы `AuthBootstrap` читает `localStorage`, проверяет срок действия (`utils/jwt.ts → isExpired`) и восстанавливает сессию в Redux — поэтому после перезагрузки вы остаётесь вошедшим.
4. Защищённые запросы добавляют `Authorization: Bearer …`. Если сервер ответил 401 — `useFailure` выходит из аккаунта и ведёт на `/login`.

**Защита на интерфейсе:** если не вошли и нажали «удалить» или «+», вас перенаправляет на `/login` (`guard` в `OrdersView`).

**Обёртки `localStorage` в try/catch** — в приватном режиме браузера доступ может бросать ошибку.

**Честная оговорка для собеседования:** токен в `localStorage` уязвим к XSS; безопаснее `httpOnly`-cookie. Здесь это сделано, потому что ТЗ прямо требует Web Storage. И ещё: JWT не шифруется, а подписывается; пароли хранятся только как bcrypt-хеш; в продакшене трафик должен идти по HTTPS.

## 10. Интернационализация (i18n)

**Что делаем.** Собственная небольшая реализация без библиотек:
- `i18n/locales/{ru,uk,en}.json` — тексты интерфейса (их и редактируем). `i18n/dictionaries.ts` — только подключение JSON и тип: эталон ключей — `ru.json`, поэтому если в `uk.json`/`en.json` пропущен ключ, TypeScript не скомпилирует.
- `I18nProvider` даёт хук `useI18n()` → `t('ключ')`, `months`, `weekdays`, `productsWord(n)`.
- Язык хранится и в `localStorage`, и в **cookie** — cookie нужна, чтобы сервер при SSR сразу отдавал правильный язык (без «мигания» ru → en).

**В видео:** переключите RU → UA → EN, перезагрузите страницу — язык сохранён.

## 11. Lazy Loading

Код загружается только тогда, когда нужен:
- `next/dynamic` — графики (`StatsLoader` → `StatsView`), карта (`MapLoader` → `MapView`), формы и попап (`OrdersView`). Библиотеки Recharts и Leaflet не попадают в основной бандл.
- `ssr: false` для графиков и карты — они работают только в браузере (нужен `window`).
- `loading="lazy"` для картинок (`ProductThumb`). Сами картинки лежат в `frontend/public/img/`, в базе хранится только имя файла.

**Доказательство:** после `npm run build` страница `/stats` весит ≈ 4.8 кБ, а не сотни (библиотека в отдельном чанке). В DevTools → Network видно, что чанк графиков грузится только при переходе на «Статистику».

## 12. Графики, карта, пользователи, настройки

- **Графики** (`StatsView.tsx`, Recharts): горизонтальная столбчатая диаграмма сумм приходов (переключатель валюты) и круговая — продукты по типам. Подписи столбцов — номер и обрезанное название (`utils/text.ts → truncate`), полное название видно в подсказке; приходы отсортированы по сумме. Высота графика растёт с числом приходов, а при большом количестве блок прокручивается. Данные готовят чистые функции `utils/stats.ts` (они покрыты тестами).
- **Карта** (`MapView.tsx`, Leaflet + OpenStreetMap): маркер на каждый приход с координатами; клик показывает название и количество продуктов. Использован `CircleMarker`, а не стандартная иконка: в бандлерах иконки Leaflet часто «ломаются».
- **Пользователи** (`UsersView.tsx`): список из `GET /api/users`. Нужен токен, а он есть только в браузере, поэтому данные грузятся на клиенте, а не при SSR.
- **Настройки** (`SettingsView.tsx`): язык, имя пользователя, срок действия сессии (из `exp` токена) и выход.

## 14. Стили: БЭМ + Bootstrap

- **Bootstrap** — готовые кнопки (`btn`), поля (`form-control`), списки (`form-select`), сообщения (`alert`). Цвета его кнопок переопределены переменными самого Bootstrap (`--bs-btn-bg` …) под фирменный зелёный. Сетку Bootstrap не используем: раскладка на CSS Grid и Flexbox.
- **БЭМ** (`блок__элемент--модификатор`): `order-row`, `order-row__main`, `order-row--compact`, `popup__footer--accent`, `nav-menu__link--active` … Один блок — одна ответственность, без глубоких селекторов.
- Адаптив: на экранах < 900 px боковое меню становится горизонтальным, панель прихода уходит под список.
- `prefers-reduced-motion` отключает анимации для людей, которым они мешают.

## 15. Docker

- `backend/Dockerfile` — Node 22, `npm ci --omit=dev`, запуск через `tsx`.
- `frontend/Dockerfile` — **многоэтапный**: этап `build` собирает Next в режиме `standalone`, финальный образ содержит только нужное (маленький и быстрый).
- `docker-compose.yml` — `db` (MySQL с `init.sql` и healthcheck) → `backend` (ждёт здоровую базу) → `frontend`.
- Адрес WebSocket вшивается при сборке (`NEXT_PUBLIC_SOCKET_URL`), потому что его использует браузер, а не сервер.
- Версия Node внутри образов (22) не зависит от версии на вашем компьютере.

**Команда:** `docker compose up --build` → http://localhost:3000.

## 17. Полезные команды для демонстрации

# токен
TOKEN=$(curl -s -X POST localhost:4000/api/auth/login -H 'Content-Type: application/json' \
  -d '{"login":"admin","password":"admin123"}' | python3 -c "import sys,json;print(json.load(sys.stdin)['token'])")
